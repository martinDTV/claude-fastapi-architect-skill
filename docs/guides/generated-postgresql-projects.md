# Generated PostgreSQL projects: persistence, migrations and verification

How a backend generated by `scripts/design_fastapi.py` from a contract with `persistence.kind: postgresql` stores
data, how its schema evolves, and how to verify it against a real PostgreSQL without trusting anything the tool
did not check. The example is `plugins/fastapi-architect/examples/generated/orders-platform/` (generated from
`examples/specs/orders-platform.json`).

## What the generator produces

| Piece | Where | What it does |
|---|---|---|
| Declarative base with a naming convention | `src/<pkg>/core/db.py` | `pk_<table>`, `uq_<table>_<cols>`, `fk_<table>_<cols>_<referred>`, `ix_<table>_<col>`: models and migrations agree on every constraint name |
| Engine and request-scoped session | `core/db.py`, `main.py` lifespan | one `AsyncEngine` per application, one `AsyncSession` per request yielded by a dependency that rolls back on any error |
| Unit of work | per-module `service.py` | the service calls `_commit()` once per use case; repositories only stage changes (`session.add`, `session.delete`); an `IntegrityError` on commit is rolled back and answered **409** `application/problem+json` |
| Mapped classes | per-module `models.py` | SQLAlchemy 2 `Mapped[...]` columns, `tenant_id` when multi-tenant, `UniqueConstraint(tenant_id, id)`, `ForeignKeyConstraint` from declared `references` (composite `(tenant_id, <fk>)` between tenant tables) |
| Alembic environment | `alembic.ini`, `migrations/env.py`, `migrations/script.py.mako` | async engine, URL from `<PKG>_DATABASE_URL`, metadata of every generated model, `compare_type=True` |
| Initial migration | `migrations/versions/<rev>_initial_schema.py` | `op.create_table` in dependency order with explicit constraint names, indexes on tenant and foreign-key columns; `downgrade` drops in reverse order. The revision id is derived from the contract digest, not from the clock |
| Test suite | `tests/conftest.py`, `tests/test_migrations.py`, `tests/test_<module>.py` | see below |

`create_all` is never called. Tables exist only after `alembic upgrade head`.

## Running it

```
cd <generated project>
uv sync
export ORDERS_PLATFORM_DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@localhost:5432/orders_platform
uv run alembic upgrade head
uv run uvicorn orders_platform.main:app --reload
```

No credential is generated: `.env.example` carries placeholders, the settings default has no password, and
`alembic.ini` only holds a credential-free fallback URL for offline mode.

## The generated test suite

The suite needs `DATABASE_URL` pointing at an **empty, disposable** database and refuses anything else:

1. `migrated` (session fixture) fails if the database already has tables, runs `alembic upgrade head`, and runs
   `alembic downgrade base` at the end;
2. every test runs on a fresh state: an autouse fixture truncates all tables (`TRUNCATE ... RESTART IDENTITY
   CASCADE`) after each test;
3. `test_migrations.py` asserts one head, that `compare_metadata(models, database)` is empty (unexpected schema
   changes are detected), that tables, unique constraints and foreign keys exist by name, and that
   `downgrade base` + `upgrade head` is repeatable with `alembic current` reporting the generated revision;
4. `test_<module>.py` exercises every declared operation through the HTTP boundary, including a 409 with no row
   persisted when a reference points at a missing row, and, for multi-tenant contracts, 403 for another tenant's
   path with the same key, empty listings across tenants, and a 409 when a reference points at another tenant's
   row (composite foreign key).

Parents are created through their own API: `create_customer(...)` is imported by `tests/test_orders.py`, and
`create_order(...)` by `tests/test_billing.py`, so a valid payload always references real rows.

## Verifying a generated backend against a throwaway PostgreSQL

The plugin ships an opt-in test that does this end to end through the v1.9 trust model:

```
FA_DESIGN_PG=1 FA_DESIGN_PG_EVIDENCE=/tmp/evidence python3 -m unittest tests.test_design_v20_postgresql -v
```

It needs `initdb`, `pg_ctl`, `psql` and `uv`. It creates a cluster under a temporary directory (`trust`
authentication on 127.0.0.1, a free port, `fsync=off`), creates an empty database, generates `orders-platform`
into a temporary target, and runs the generated suite with `--authorize-execution --trust fixture` semantics:
`LocalProcessExecutor` (process hygiene: a copy of the project, fresh `HOME`, reduced environment, no shell,
allow-listed programs, closed stdin, timeouts; **not** a sandbox, no network or filesystem isolation) and the
pytest JUnit adapter (report bound to the run by a nonce). `DATABASE_URL`, `UV_CACHE_DIR` and
`UV_PYTHON_INSTALL_DIR` are passed through so `uv run` syncs the environment from the local cache inside the copy.
A negative control mutates a model and asserts that the drift test fails. The cluster is stopped and deleted
afterwards. The evidence of the run that accompanies this increment is in
`plugins/fastapi-architect/examples/generated/VERIFICATION.md`.

By hand, the same thing is:

```
python3 scripts/design_fastapi.py plugins/fastapi-architect/examples/specs/orders-platform.json --target /tmp/orders \
    --authorize-execution --trust fixture --test-command "uv run --group dev pytest -q" \
    --env-passthrough DATABASE_URL,UV_CACHE_DIR,UV_PYTHON_INSTALL_DIR --format markdown
```

with `DATABASE_URL` set to an empty database you own. Without `--authorize-execution` nothing is executed and the
report says so.

## Limits

- One initial migration is generated; later migrations are yours (`uv run alembic revision --autogenerate` works
  because the metadata and the naming convention are complete).
- Isolation between tenants is application scoping plus composite foreign keys. No row-level security, no schema or
  database per tenant, no resource-level authorization: the report's `guarantees` block says so explicitly.
- The `migrated` fixture leaves `alembic_version` behind after `downgrade base`; the database is otherwise as found.
- `uv.lock` is not generated (resolution needs the index); the version ranges in `pyproject.toml` are explicit and
  `uv lock` produces the lockfile in one step.
