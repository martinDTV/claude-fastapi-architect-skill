# tenant-projects

Generated by FastAPI Architect (design engine v2.0) from the `tenant-projects` contract (digest `90251d20a00e`); style **modular_monolith**.

## Why this structure

- modules by business capability with declared dependencies: medium scope, team of 4; one deployable keeps transactions and operations simple

Rejected alternatives:

- `microservices`: independent deployment is not stated; network partitions, distributed consistency and per-service operations are paid for only when deployment independence is required
- `hexagonal`: 0 outbound integration(s) and no high-criticality dependency: ports and adapters would add indirection without a second implementation to protect
- `layered`: a single package by layer blurs ownership once several capabilities share services and repositories

## Database, roles and migrations

Two database roles, two URLs. The **owner** runs the migrations (`TENANT_PROJECTS_MIGRATIONS_DATABASE_URL`); the **application
role** `tenant_projects_app` (`TENANT_PROJECTS_DATABASE_URL`, name in `TENANT_PROJECTS_APP_ROLE`) only reads and writes rows. Create the application role
before the first migration (roles are provisioning, not migrations; the migration verifies it exists and cannot bypass
row-level security):

```
CREATE ROLE tenant_projects_app LOGIN PASSWORD '...' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOINHERIT;
```

Then, as the owner:

```
uv run alembic upgrade head      # tables, indexes, GRANTs, ENABLE + FORCE ROW LEVEL SECURITY and one policy per table
uv run alembic current
uv run alembic downgrade base
```

The test suite needs `DATABASE_URL` (the application role) and `TENANT_PROJECTS_MIGRATIONS_DATABASE_URL` (the owner) pointing at the same
**empty, disposable** database: it migrates and truncates as the owner, runs the API as the application role, and
`tests/test_rls.py` proves the isolation with raw SQL through that role (no context: no rows; context bound to the
transaction; another tenant's rows unreachable; the role cannot lift the protection; concurrent tenants never mix).

## Tenants and API keys

`TENANT_PROJECTS_API_KEYS` is a JSON object mapping each API key to its grant: `{"tenant_id": ..., "subject": ..., "roles": [...]}`
(a bare tenant id is still accepted). A request to `/api/v1/tenants/{tenant_id}/...` is accepted only when the key
presented in `X-API-Key` is bound to that tenant (403 otherwise); every repository call is scoped by that tenant id.
Row-level security in PostgreSQL enforces the same boundary inside the database (see above).

## Authorization (model `roles_and_ownership`)

Roles come with the identity (the key grant). Each route carries the principal admitted
for its operation (`CanCreate`, `CanGet`, ...); an operation with a role list refuses, with 403, a principal without one of
them:

- `delete`: admin

Owned entities (`tasks.Task`) record the creating principal in `owner_id` (never taken from the request). Visibility is
**tenant**: every member of the tenant reads them; only the owner (or an admin) updates or deletes them, 403 otherwise.
Admin roles: admin. The checks live in the service and the repository (`core/authz.py`), not in the router.
