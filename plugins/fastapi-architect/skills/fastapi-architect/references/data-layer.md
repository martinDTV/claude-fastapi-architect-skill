## Choosing the stack

| Need | Choice |
|---|---|
| Relational data, default | PostgreSQL + SQLAlchemy 2.0 async + asyncpg + Alembic |
| Team or codebase already sync, mostly blocking libraries | SQLAlchemy 2.0 sync + psycopg 3, path operations declared with `def` |
| Very simple models, team prefers less boilerplate | SQLModel is acceptable in Stage 0 and 1; keep separate Create/Update/Read models anyway |
| Document data with no relational needs | MongoDB with Beanie or the async PyMongo driver |

Record the choice in an ADR. Do not mix sync and async database access in the same request path.

## Models

- SQLAlchemy 2.0 declarative style with `Mapped[...]` and `mapped_column(...)`. No legacy `Column` without `Mapped`.
- One `Base` in `core/db.py` with a metadata naming convention (see `project-structure.md`). Without it, Alembic generates unnamed constraints that cannot be dropped portably.
- Timestamps: `DateTime(timezone=True)` with `server_default=func.now()`; `updated_at` with `onupdate=func.now()`.
- Money: `Numeric(precision, scale)` mapped to `Decimal`.
- Primary keys: integer identity is fine internally. If IDs are exposed publicly and enumeration matters, add a UUID public identifier or use UUID primary keys.
- Enums: Python `StrEnum` with `Enum(..., native_enum=False)` or a check constraint, so adding a value does not require a type migration.
- Add indexes for every foreign key and every column used in frequent `WHERE`/`ORDER BY`.
- Models of one module never declare `relationship()` to models of another module. Store the foreign ID.

## Sessions and transactions

```python
# core/db.py
async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    async with request.app.state.session_factory() as session:
        yield session
```

- The session factory is created once in `lifespan` with `expire_on_commit=False` and stored on `app.state`.
- One session per request, injected with `SessionDep`. Because dependencies are cached per request, the service and its repositories share the same session and transaction.
- The service commits once at the end of each write use case. If an exception escapes, the session closes without commit and everything rolls back.
- Repositories call `session.add` and `await session.flush()` (to get generated IDs) but never `commit` or `rollback`.
- Never create a global session or reuse a session across requests or tasks.
- Background workers create their own session from the same factory for each job.

For use cases that must also publish an event, write the event to an `outbox` table in the same transaction (see `architecture-decisions.md`).

## Repositories: how much abstraction

| Stage | Repository style |
|---|---|
| 0 | None. Query in the route or a small function |
| 1 | Concrete class per aggregate with intention-revealing methods, returning ORM models |
| 2 | `Protocol` port in `ports.py`; SQLAlchemy adapter maps ORM models to domain entities; in-memory fake for tests |

Do not write a generic `BaseRepository[T]` with `get/list/create/update/delete` and `**filters`. It hides query cost, cannot express joins or locking, and every real query works around it.

Write queries with the 2.0 `select()` API and `session.scalars()` / `session.scalar()` / `session.execute()`. No `session.query()`.

## Relationships and N+1 queries

- In async SQLAlchemy, implicit lazy loading raises `MissingGreenlet`. Declare relationships with `lazy="raise"` so accidental lazy loads fail loudly in tests instead of in production.
- Load what you need explicitly: `selectinload()` for collections, `joinedload()` for many-to-one.
- Never loop over parents and query children one by one.
- For read-heavy endpoints returning large shapes, select only the needed columns and build the response schema directly.

```python
stmt = (
    select(Order)
    .where(Order.customer_id == customer_id)
    .options(selectinload(Order.items))
    .order_by(Order.created_at.desc())
    .limit(limit)
)
orders = (await session.scalars(stmt)).all()
```

## Migrations with Alembic

- Initialize with the async template: `uv run alembic init -t async migrations`.
- In `migrations/env.py`, set `target_metadata = Base.metadata` and import every module's `models` so autogenerate sees all tables. Read the database URL from `get_settings()`, not from `alembic.ini`.
- Every schema change is a migration. Never use `Base.metadata.create_all()` outside tests.
- Always review autogenerated migrations: autogenerate misses renames (it emits drop and add), server defaults and some type changes.
- Migrations must be backward compatible with the currently deployed code (expand, migrate data, contract):
  1. Add the new column as nullable or with a default; deploy code that writes both.
  2. Backfill in batches.
  3. Switch reads; then drop the old column in a later release.
- Run migrations as a separate deploy step (CI job, Kubernetes Job, init container), never at application startup with multiple replicas racing.
- Data migrations that touch many rows run in batches and are idempotent.

## Performance and pooling

- Pool size per process: `pool_size + max_overflow` multiplied by worker processes and replicas must stay under the database's connection limit. With many replicas, put PgBouncer (transaction mode) in front and disable prepared statement caching for asyncpg if required by the pooler.
- `pool_pre_ping=True` to survive dropped connections.
- Set statement timeouts at the database role or connection level for API traffic.
- Use `EXPLAIN ANALYZE` before adding caching. Most slow endpoints are a missing index or an N+1.
- Cache (Redis) only read paths with measured need, with explicit TTLs and invalidation on write.

## Multi-tenancy

Decide early and record it in an ADR; it is expensive to change.

| Model | Use when |
|---|---|
| Shared tables with `tenant_id` column | Many small tenants, default choice. Enforce with a tenant dependency that every repository query filters on, and consider PostgreSQL row-level security as a second line of defense |
| Schema per tenant | Tens to low hundreds of tenants needing stronger isolation or per-tenant customizations |
| Database per tenant | Few large tenants, contractual isolation, per-tenant backups or regions |

Resolve the tenant once per request (from the token or subdomain) in a dependency and pass it explicitly; never read it from a global.

## Sessions and engines: what the auditor checks and what it cannot see (v1.4)

The static auditor (`scripts/audit_fastapi.py`, category `sqlalchemy`) encodes the rules above as review signals; `references/audit-rules.md` lists them. The distinctions that matter when reading its report:

- **Factory versus instance.** A module-level `sessionmaker(...)`, `async_sessionmaker(...)` or `scoped_session(...)` is the recommended global. A module-level `Session(engine)`, `AsyncSession(engine)` or `SessionLocal()` is a shared instance and is reported (`SA_SESSION_MODULE_GLOBAL`), also when the factory is imported under an alias from another module.
- **Lifetime.** A session built from a factory must end: context manager, `close()` in `finally`, or ownership handed to a caller. A yield-based dependency without `close()` is the classic leak (`SA_SESSION_NOT_CLOSED`).
- **Concurrency.** One `AsyncSession` per task. Passing the request session to several coroutines in `asyncio.gather`, or to `create_task`/task groups/threads, is reported (`SA_SESSION_SHARED_CONCURRENTLY`); the fix is a session per task from the factory, not a lock.
- **Await and blocking.** An `AsyncSession` coroutine method without `await` never runs (`SA_ASYNC_SESSION_NOT_AWAITED`); a synchronous `Session` inside `async def` blocks the loop (`SA_SYNC_SESSION_IN_ASYNC_DEF`). Both rely on visible types: annotate dependencies (`SessionDep = Annotated[AsyncSession, Depends(get_session)]`) and the tool becomes precise; leave `db=Depends(get_db)` untyped and it can only guess from the name.
- **Engines and schema.** `create_engine` inside a handler builds a pool per request (`SA_ENGINE_CREATED_PER_CALL`); `metadata.create_all()` in application code bypasses Alembic (`SA_CREATE_ALL_AT_RUNTIME`). Both are fine in tests, which the tool classifies separately.

Not determinable statically: whether an untyped object is a session, whether a session stored on `app.state` or `self` is used concurrently, lazy-load strategies at query time, and anything that happens inside helpers called from the handler. Confirm those with the pool metrics and the concurrency tests in `references/testing-matrix.md`.

### v1.5 additions the auditor now follows across functions
- A session's kind is known wherever it travels: `Depends(get_session)` return/yield types and caller arguments type the parameters of services and repositories, so an un-awaited `AsyncSession` method or a blocking sync `Session` call is reported inside helpers too, marked `evidence: inferred` when the type came from a caller.
- `with session.begin()` inside a block that already began a transaction on the same session raises `InvalidRequestError`; use `begin_nested()` for a savepoint (`TX_NESTED_BEGIN`).
- Relationships with the implicit `lazy="select"` strategy accessed under `AsyncSession` raise `MissingGreenlet`; declare `lazy="selectin"`, use `selectinload`/`joinedload` per query, or `lazy="raise"` to make the dependency explicit (`SA_ASYNC_LAZY_LOAD_RISK`). `examples/tenant-ledger/tests/test_antipatterns.py` reproduces both the error and the fix.
